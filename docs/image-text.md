# 贴图流程（插件 1.9.5）

## 准备与更新素材
在配置的输出根目录下按文章标题建文件夹，包含 `标题.txt`、`正文.txt`、`images/01.png` 等顺序原图、`贴图文章包.json`。按数字排序，首图为封面。支持 1–20 张 PNG/JPEG，单图最大 10 MB、合计最大 32 MB；平台实际限制仍需校验。保留原图，不擅自压缩或合并正文空行。

素材 Agent 负责生成包；修改标题、正文、图片后也由它重新生成，不要求使用者编辑 JSON。保持稳定 articleId。生成脚本不覆盖现有输出；更新时先备份旧包，再生成新包。不要把备份图片留在 images/ 中。

```sh
python3 scripts/build_image_post.py --folder '/输出根目录/文章标题' --article-id stable-article-id --output '/输出根目录/文章标题/贴图文章包.json'
```

上述命令从仓库根目录执行；只安装 Skill 时也有同名脚本。包为 schemaVersion=2、type=newspic；images 包含原图 dataUrl 与 SHA-256，不依赖素材 Agent 的本地路径。接收微信号、署名和登录信息不放进包。正文保留 LF、空行和空格；CRLF 需与用户确认转换后打包。

## 使用者操作
1. 登录公众号后台，新建“贴图”，停留在空白编辑页。已有同篇草稿则打开该草稿，不重新导入到其他内容上。
2. 从 Chrome 工具栏打开插件，选“贴图”tab。首次填写本机设置。
3. 选择 JSON 包，核对标题、正文字符数、图片数量和顺序。贴图首图固定为封面，缩略图不是换序按钮。
4. 点击“保存草稿并通过微信号预览”。插件按顺序上传、填标题正文、保存、刷新读回核对。
5. 有微信号预览入口则发送一次；只有扫码预览时，以“草稿已保存并核对”结束，用户去草稿箱审核、手工发表。不必为了结束流程扫码。

`运行步骤.txt` 面向插件使用者，写操作步骤与交付状态；给素材 Agent 的打包指令放在 Skill/Agent 指令中，不混为一份说明。

## 核对与恢复
正文逐字、空格、空行和图片顺序都核对；不能只看图片数量。页面没有独立作者/原创入口时记录未提供，不声称已开启。保存失败保留平台提示；未确认保存时不刷新丢失现场或重复提交。已核验草稿可以直接继续预览，不重复上传或保存。

非空内容须唯一匹配同篇历史才能更新。图片已上传的中断任务须核对已有图片前缀；不得认领来源不明的图片。换包不绕过防重发记录，`preview-unknown` 不重发。诊断可在运行中只读下载；不要公开上传个人诊断。

## 已验证范围

## 已发表贴图修改（1.10.0）

这与草稿替换不同。在公众号打开已发表内容的“修改”页面，插件选择贴图 tab、导入新包，勾选“修改已发表贴图”。点“核对已发表文章的新旧内容”，检查新旧文字及图片，之后点“按上述差异填入，提交由我完成”。

插件备份页面原文和原图地址，仅通过页面已有换图控件替换图片，核对文字和图片顺序后停为 published-ready。不会保存、预览或提交修改；使用者在公众号页面审核并手动提交，修改次数与字段限制以平台当前页面为准。不要把本地填入成功当作线上文章已更新。

本版保持图片数量不变。原图校验记录可用时仅替换变化的图片；记录不足时展示全部新旧图片，须核对后才执行。未找到唯一换图入口、字段只读、页面在核对后变化、平台未完成上传时停止并保留诊断，不删除原图以绕过限制。本功能通过隔离浏览器模拟测试，尚未在用户的已发表页面实测。

### 1.10.1：页面只有删除和追加时
若没有替换按钮但有追加上传和图片删除入口，先上传并核对整组新图，再逐张移除旧图，最终图片顺序与包一致。不在新图未齐时删除原图；中断后只恢复已有图片证据匹配的进度，不重复上传。临时新旧图合计超过 20 张时停止，不用先删除来绕过容量限制。提交修改仍由用户手动完成。
失败的已发表修改记录不能用来证明旧图等于新包；只有已完成核验的图片记录可作为判断图片未变的依据。该策略已按诊断中的工具栏结构做本地模拟验证，真实页面仍待核验。
